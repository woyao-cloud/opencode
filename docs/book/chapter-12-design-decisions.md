# 第 12 章 · 设计决策与权衡回顾

全书最后一章，我们回顾 opencode 架构中的关键设计决策，分析每个决策的"为什么"和"代价是什么"。

## 12.1 关键设计决策汇总

| 决策 | 选择 | 替代方案 | 选择理由 |
|------|------|---------|---------|
| 效应系统 | Effect-TS | 原生 Promise/async | 类型安全的错误处理、依赖注入、结构化并发 |
| 事件驱动 | Event Bus + SessionEvent | 请求-响应式 | 多消费者独立订阅、解耦 UI/日志/同步 |
| LLM 调用单位 | Step | Turn | 精确对应一次 API 调用，多 Step 组成一个用户请求 |
| 工具定义 | 类型安全 Schema | 自由格式 JSON | 编译时类型检查、运行时验证、自动编解码 |
| 上下文压缩 | AI 生成摘要 | 滑动窗口/截断 | 更高信息密度、保留关键决策和理由 |
| 指令文件 | 文件系统层级发现 | 数据库/向量存储 | 零配置、利用文件系统层级结构、开发者熟悉 |
| 多 Agent | Task 工具 + Subagent | 固定 Agent 图/工作流 | 灵活派发、AI 自主决策何时使用 Subagent |
| 流式协议 | 统一 LLMEvent | 各 Provider 独立处理 | 上游代码 Provider 无关、新增 Provider 只需适配器 |
| 权限控制 | 权限键分组 + 双层控制 | 按工具独立控制 | 减少用户决策负担、Subagent 权限继承 |
| 日志系统 | 自研轻量实现 | winston/pino 等库 | 零外部依赖、低开销、与 Tag 机制深度集成 |

## 12.2 架构取舍分析

### 为什么选择 Effect-TS？

Effect-TS 是 opencode 最"重"的架构依赖。它的学习曲线陡峭，类型错误信息复杂，编译速度受影响。选择它的核心理由是：

**类型安全的错误处理**：在 AI 编程助手中，错误是常态而非异常——API 调用可能失败、工具执行可能出错、文件可能不存在。Effect 的 `Effect<Success, Error, Requirements>` 类型强制每个操作声明它可能产生什么错误，编译器确保所有错误路径都被处理。

**依赖注入（Layer）**：opencode 需要在测试中替换真实的文件系统、HTTP 客户端、LLM API。Effect 的 Layer 系统使得依赖替换是类型安全的——如果测试提供的模拟层缺少某个依赖，编译器会报错。

**结构化并发（Fiber）**：工具并发执行、Subagent 并发调度需要可靠的并发控制。Effect 的 Fiber 确保子效应的生命周期受父效应控制——父效应被中断时，所有子效应也被清理。

代价是：团队需要投入时间学习 Effect-TS，新成员的入门门槛较高，类型错误信息有时难以解读。

### 为什么用事件驱动而非请求-响应？

请求-响应模式更简单：用户输入 → 处理 → 返回结果。但 opencode 需要多个消费者同时关注同一组数据——UI 需要渲染、日志需要记录、同步系统需要持久化、Trace 需要追踪。

事件驱动使得每个消费者独立订阅事件流，互不干扰。新增消费者（如评测数据收集器）不需要修改核心流程代码。

代价是：事件顺序和一致性需要仔细管理。事件是否按正确顺序到达？消费者是否看到了一致的状态快照？这些问题在请求-响应模式中不存在。

### 为什么 Step 是核心抽象而非 Turn？

Turn（一问一答）是更直观的抽象。但 AI 调用工具后需要继续处理工具结果，一个用户消息可能触发 3-5 次 LLM 调用。Step 精确对应一次 API 调用，使得：
- Token 消耗按 Step 追踪（而非按 Turn 聚合）
- 错误处理按 Step 粒度（一次 API 调用失败不影响同一 Turn 中的其他 Step）
- 工具调度在 Step 边界发生（工具结果注入后开启新 Step）

代价是：Step 概念需要向用户解释。用户看到的是"一个回复"，但内部可能是多个 Step。

### 为什么用 AI 生成摘要而非滑动窗口？

滑动窗口（只保留最近 N 条消息）实现简单，但会丢失窗口之前的全部上下文。AI 生成摘要保留了关键决策、重要文件路径和未解决问题的信息，信息密度远高于原始消息。

代价是：压缩本身消耗 Token（需要一次额外的 LLM 调用），压缩质量依赖 AI 的理解能力，压缩可能遗漏 AI 认为不重要但实际重要的细节。

### 为什么用文件系统做 Memory 而非向量数据库？

向量数据库 + RAG 是流行的 AI Memory 方案。opencode 选择文件系统（AGENTS.md / CLAUDE.md）的理由是：
- **零配置**：开发者只需要创建 Markdown 文件，不需要运行数据库、构建索引
- **层级结构**：文件系统的目录树天然提供了"作用域"——根目录的指令对全局生效，子目录的指令对局部生效
- **开发者熟悉**：每个开发者都知道如何创建和编辑 Markdown 文件
- **Git 友好**：指令文件可以被版本控制，随代码一起演进

代价是：不支持语义搜索（"找到与认证相关的所有记忆"），不支持自动关联（"这段代码和那段记忆相关"）。对于需要复杂记忆检索的场景，文件系统方案力不从心。

## 12.3 未来演进方向

基于当前架构的分析，opencode 可能的演进方向包括：

- **更智能的压缩**：当前压缩是"全量总结"，未来可能支持"选择性压缩"——只压缩不再需要的部分，保留高价值信息
- **Memory 的语义化**：在文件系统基础上增加可选的语义索引层，支持"找到与当前任务相关的所有历史记忆"
- **Agent 间通信**：当前 Subagent 只能通过任务描述和结果文本通信，未来可能支持更结构化的 Agent 间消息传递
- **流式工具的流式结果**：当前工具结果在工具完成后一次性注入，未来可能支持工具在执行过程中流式返回中间结果
- **跨 Session 学习**：当前 Memory 以静态指令文件为主，未来可能支持从多次会话中自动提取模式和偏好

---

## 本章小结

opencode 的架构是一系列有意识的设计决策的结果。每个决策都有明确的理由，也有明确的代价。理解这些决策及其权衡，是理解 opencode 为什么"长这样"的关键。架构不是凭空产生的——它是在具体约束（类型安全、多模型支持、长对话体验、可观测性）下，对多种可能方案进行权衡后的选择。
