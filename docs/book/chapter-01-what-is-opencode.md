# 第 1 章 · opencode 是什么

## 1.1 项目定位

opencode 不是一个单一的 AI 编程工具，而是一个**AI 编程助手框架**。它提供了一套完整的基础设施，让开发者可以构建、定制和运行 AI 编程助手。你可以把它理解为"编程助手领域的操作系统"——它管理会话、调度工具、接入模型、协调多个 AI Agent 协作，而上层的终端界面、Web 应用、桌面应用都是基于这套基础设施构建的。

这个定位意味着 opencode 需要解决一些比普通 AI 聊天应用更复杂的问题：

- 如何让 AI 安全地执行文件读写、命令运行等敏感操作？
- 如何在长达数百轮的对话中保持上下文不退化？
- 如何同时接入 Anthropic、OpenAI、AWS Bedrock、Google Vertex 等十几个模型提供商？
- 如何让多个 AI Agent 并发协作而不互相干扰？
- 如何让每一次 AI 调用的行为都可观测、可评测？

## 1.2 核心能力全景

opencode 的能力可以从五个维度来理解：

### 对话式编程

用户用自然语言描述需求，AI 理解意图后直接操作文件系统——读取代码、编辑文件、运行命令、搜索代码库。这不是简单的"问答"，而是"执行"。AI 在对话过程中实际修改项目代码，每次修改都产生可审查的 Diff。

### 工具调用执行

AI 不是孤立运行的。它拥有一套类型安全的工具系统，包括：执行 Shell 命令、读写文件、搜索代码、发起 Web 请求、调用 LSP 语言服务器、操作 Todo 任务列表等。每个工具的输入输出都有 Schema 约束，执行过程有权限控制。

### 多 Agent 协作

opencode 支持定义多个 Agent，每个 Agent 有不同的职责、权限和模型配置。主 Agent 可以通过 Task 工具派发子任务给 Subagent，多个 Subagent 可以并发执行。Session Fork 机制允许从对话的任意节点分支出去探索不同方案。

### 多模型接入

通过统一的 Provider 抽象层，opencode 可以接入几乎所有主流 LLM 提供商。模型的定义、能力声明、成本信息、变体配置都有统一的数据结构。消息在发送给不同提供商之前会经过转换管道进行归一化处理。

### 可观测性

每一次 AI 调用、每一个工具执行、每一个会话事件都被记录在结构化的日志和事件流中。OpenTelemetry 集成提供了标准化的 Span 追踪。这些数据既用于调试，也用于与评测团队对齐 Agent 行为。

## 1.3 技术栈概览

opencode 的技术选型反映了它对类型安全、效应管理和运行时性能的重视：

**TypeScript** —— 全项目使用 TypeScript，从工具参数到 API 响应都有编译时类型检查。工具系统的核心就是 Effect Schema，它同时提供了运行时验证和 TypeScript 类型推导。

**Bun** —— 选择 Bun 而非 Node.js 作为运行时，主要是为了启动速度和原生 TypeScript 支持。Bun 的快速文件 I/O 对频繁读写项目文件的操作至关重要。

**Effect-TS** —— 这是 opencode 最关键的架构依赖。Effect 是一个 TypeScript 的效应系统库，提供了：
- 可组合的效应类型（Effect<Success, Error, Requirements>）
- 依赖注入（Layer 系统）
- 结构化并发（Fiber）
- Schema 系统（同时用于验证和类型推导）
- 流处理（Stream）

opencode 大量使用 Effect 来管理副作用：文件 I/O、HTTP 请求、Shell 命令执行、LLM API 调用都被建模为 Effect，通过 Layer 系统注入依赖，使得测试时可以替换为模拟实现。

**SolidJS** —— Web 应用端使用 SolidJS，利用其细粒度响应式系统来高效渲染会话消息流、上下文用量指示器等动态 UI。

## 1.4 与同类工具的架构差异

opencode 的架构有几个区别于常见 AI 编程工具的设计选择：

### 事件驱动而非请求-响应

许多 AI 聊天应用采用简单的请求-响应模式：用户发消息 → 等 AI 回复 → 展示结果。opencode 采用事件驱动架构：整个会话被建模为事件流（SessionEvent），包括消息创建、Part 更新、Step 开始/结束、工具状态变化等。这种设计使得多个消费者（终端 UI、Web 应用、日志系统）可以独立订阅和响应同一组事件。

### Step 而非 Turn

opencode 用"Step"而非"Turn"作为 LLM 调用的基本单位。一个 Step 代表一次完整的 LLM API 调用——从发送请求到收到 finish_reason。如果 AI 决定调用工具，工具执行完毕后会开启新的 Step 继续对话。这种抽象比"Turn"更精确，因为一个用户消息可能触发多个 Step（多次 LLM 调用）。

### 工具作为一等公民

工具不是外挂在 AI 之上的插件，而是框架的核心抽象。每个工具都有类型安全的参数和返回值定义、生命周期状态机、权限声明和 UI 渲染规则。工具注册表是静态编译的，新增工具需要显式定义。

### 效应系统作为基础设施

Effect-TS 不仅是工具库，而是贯穿整个框架的基础设施。从文件操作到 HTTP 请求到 LLM 调用，所有副作用都通过 Effect 管理。这意味着：
- 错误处理是类型安全的（编译器知道每个操作可能抛出什么错误）
- 依赖是可替换的（测试时注入模拟层）
- 并发是结构化的（Fiber 的生命周期受父效应控制）

## 本章小结

opencode 是一个 AI 编程助手框架，它用事件驱动架构、类型安全工具系统、效应管理基础设施和多 Agent 协作模型，构建了一套完整的 AI 编程基础设施。接下来的章节将逐一展开这些机制的具体实现。
