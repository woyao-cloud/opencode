# 第 8 章 · C 端体验优化

C 端（用户端）体验是 AI 编程助手能否被用户接受的关键。本章聚焦 opencode 在首 Token 延迟、流式输出流畅度、工具失败降级和静默失败检测四个维度的设计决策与实现策略。

## 8.1 首 Token 延迟（TTFT）优化

首 Token 延迟（Time To First Token）是用户感知响应速度的核心指标——从按下回车到看到第一个 AI 输出的文字，这段时间决定了用户对"AI 快不快"的直觉判断。

### 流式传输：边收边渲染

opencode 采用流式 HTTP 请求（SSE），AI 每生成几个 Token 就立即发送，而非等完整响应生成完毕。框架在收到第一个 `text-delta` 事件时立即渲染，用户几乎在 AI 开始"思考"的同时就看到文字开始出现。

### 非阻塞 UI

在 TUI 模式下，流式事件的接收和 UI 渲染在同一事件循环中完成。没有"等待完整响应 → 一次性渲染"的阻塞点。每个 `text-delta` 到达后立即追加到终端输出。

### 缓存加速

Anthropic Prompt Caching（见第 5 章）对 TTFT 有显著影响。被缓存的 System Prompt 和工具定义不需要每次重新处理，减少了 API 端的处理时间。在长对话中，缓存命中可以将 TTFT 降低 30-50%。

### 模型选择的影响

不同模型的 TTFT 特性不同。opencode 允许用户和 Agent 选择模型，实际上也允许在"快但可能不够强"和"强但可能稍慢"之间做权衡。框架本身不做 TTFT 的硬性保证，但通过流式传输和缓存优化，确保无论选择哪个模型，响应都是渐进呈现的。

## 8.2 流式输出流畅度

流畅度不仅仅是"快"，还包括输出的连贯性和视觉稳定性。

### Text Delta 合并策略

LLM 的流式响应以不定长的文本块到达——有时一个词，有时几个字符。如果每个 delta 都触发独立的 UI 更新，会导致视觉抖动和不连贯。

opencode 的合并策略是：
- 同一个 Provider Metadata 上下文内的连续 text-delta 被合并到同一个 TextPart 中
- 只有当 Provider Metadata 发生变化（如切换到不同的内容块）时才创建新的 TextPart
- 合并后的文本在 UI 中作为连续段落渲染

### Reasoning 增量展示

支持推理（Thinking）的模型会在文本输出之前先输出推理内容。opencode 将推理内容以差异化样式展示（斜体 + 灰色），让用户区分"AI 在想什么"和"AI 在说什么"。

推理内容的展示是可配置的——用户可以选择隐藏推理过程，只看到最终文本输出。

### 工具状态的实时更新

工具执行过程中，框架实时更新工具状态：
- pending → running：工具开始执行，显示执行中的图标
- running → completed/error：工具执行完成，显示结果摘要和耗时

这种实时更新让用户感知到"AI 正在做事"，而非面对一个静止的屏幕等待。

## 8.3 工具失败的降级策略

工具执行可能因为各种原因失败。opencode 的降级策略分为三个层次：

### 第一层：错误分类

工具失败被分类为：

- **可重试错误**：临时性故障，如网络超时、Shell 命令被信号中断、文件被外部进程锁定。这类错误有重试价值。
- **不可重试错误**：永久性故障，如文件不存在、权限不足、命令语法错误。重试不会改变结果。
- **部分成功**：工具执行完成但结果不理想，如 Grep 搜索无结果、Read 文件为空。

### 第二层：错误信息结构化

工具失败时，错误信息被结构化记录，包含：
- 错误消息（人类可读的描述）
- 错误类型（分类标签）
- 截断的输出（如果工具在失败前产生了部分输出）
- 发生时间

这种结构化使得 AI 能理解失败的原因，而非只看到一个"失败了"的信号。

### 第三层：AI 自主降级

工具失败信息作为 `tool_result`（status: error）返回给 AI。AI 可以：
- 分析失败原因，调整参数后重试
- 换用其他工具达成相同目标（如 Edit 失败后改用 ApplyPatch）
- 向用户说明失败原因并请求指导
- 放弃当前路径，尝试完全不同的方案

这种"让 AI 自己处理失败"的策略比框架硬编码的降级逻辑更灵活。

### 用户可见的降级信号

在 UI 中，工具失败显示为 ✗ 标记，附带失败原因。用户可以看到 AI 遇到了什么问题，以及 AI 正在如何应对。这种透明性建立了用户对 AI 行为的信任。

## 8.4 静默失败的检测与兜底

静默失败——AI 调用看似成功但实际没有产生有效结果——是 AI 编程助手最隐蔽的问题。opencode 在多个层面检测和兜底这类失败。

### 超时检测

关键操作都有超时保护：

- **LLM API 调用**：全局超时，防止 API 挂起导致会话卡死
- **工具执行**：每个工具有独立的超时限制。Bash 命令默认 2 分钟，WebFetch 默认 30 秒
- **远程指令获取**：5 秒超时，防止慢速 URL 阻塞会话启动

超时触发后，操作被强制终止，错误信息返回给 AI 或用户。

### Provider 错误信号

LLM API 可能返回非标准的错误信号，如：
- 流意外关闭（无 finish_reason）
- 响应格式异常（无法解析的 JSON）
- 空响应（没有任何 content block）

协议适配器（见第 10 章）负责检测这些异常，将其转换为标准的 `provider-error` 事件。框架根据错误的 `retryable` 标志决定重试或终止。

### Heap 快照自动触发

opencode 内置了 Heap 快照机制：当进程内存使用超过 2GB 阈值时，自动写入 V8 Heap Snapshot 到日志目录。这不是预防措施，而是事后诊断工具——当用户报告"opencode 在某次会话中崩溃了"，开发者可以通过 Heap Snapshot 分析内存分布，定位内存泄漏或异常膨胀。

Heap 快照每分钟检查一次，连续超限不会重复写入（有 armed/lock 状态机控制频率）。

### 空响应检测

如果 LLM 返回的响应中没有任何文本内容也没有工具调用（即 AI 既没说话也没做事），框架将其视为异常响应，记录 WARN 日志并开启新的 Step 重试。

---

## 本章小结

C 端体验优化不是单一的技术点，而是贯穿流式通信、UI 渲染、错误处理和异常检测的系统工程。opencode 通过流式边收边渲染降低 TTFT、通过 Delta 合并保证视觉流畅、通过结构化错误让 AI 自主降级、通过超时和 Heap 快照兜底静默失败。这些机制共同构成了用户感知到的"这个 AI 助手好用"的体验基础。
