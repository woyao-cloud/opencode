# 第 5 章 · 多层 Context 管理

上下文管理是 AI 编程助手面临的最核心挑战之一。对话持续越长，历史消息越多，上下文窗口越紧张。opencode 通过多层架构来管理上下文——从静态的 System Prompt 到动态的对话历史，从 Token 感知到自动压缩，形成了一套完整的上下文生命周期管理机制。

## 5.1 Context 的构成

发送给 LLM 的上下文由以下几个层次叠加而成：

### 第一层：System Prompt（系统提示）

这是最"固定"的一层。System Prompt 定义了 AI 的角色、行为准则和能力边界。它包括：
- Agent 的身份描述（"你是一个专业的软件工程师..."）
- 行为规范（"修改代码前先阅读相关文件..."）
- 工具使用指南
- 输出格式要求

System Prompt 在每次 LLM 调用时都会发送，但它的大小相对固定（通常几千 Token），不会随对话增长。

### 第二层：指令文件（AGENTS.md / CLAUDE.md）

这是"半固定"的一层。指令文件的内容在会话过程中可能被新发现和注入（见第 6 章），但一旦注入就不会重复。指令文件的内容通常比 System Prompt 更具体，针对特定项目或目录。

### 第三层：对话历史（Messages）

这是"动态增长"的一层。每次用户输入和 AI 响应都被追加到消息列表中。对话历史是上下文膨胀的主要来源，也是压缩机制的主要作用对象。

### 第四层：工具执行结果

AI 调用工具后，工具的输出被作为 `tool_result` 消息注入对话。工具结果可能非常长（如 Grep 搜索返回数百行），是上下文膨胀的第二大来源。工具输出截断策略（见第 4 章）是控制这一层大小的主要手段。

## 5.2 上下文窗口感知

opencode 不会盲目发送消息直到 API 返回"上下文超限"错误。它在发送前就估算 Token 用量，并在 UI 中展示给用户。

### Token 估算

框架使用简化的估算方法：**字符数 ÷ 4 ≈ Token 数**。这不是精确计数（不同模型的分词器不同），但作为相对度量足够实用。

估算按消息角色分类统计：
- **system**：System Prompt 的 Token 估算
- **user**：所有用户消息的 Token 估算
- **assistant**：AI 文本回复的 Token 估算
- **tool**：工具输入和输出的 Token 估算

### 用量可视化

在 Web 应用和 TUI 中，上下文用量以进度环的形式展示。用户可以看到当前上下文占模型最大窗口的百分比。这个信息帮助用户判断何时需要手动触发压缩（`/compact` 命令）或开启新 Session。

### 模型限制感知

每个模型在 Provider 定义中声明了 `limit.context`（最大上下文窗口 Token 数）。框架在构建消息列表时参考这个限制，当估算用量接近限制时触发自动压缩。

## 5.3 Compaction（压缩）机制

Compaction 是 opencode 控制上下文大小的核心机制。它的基本思想是：**用 AI 自身的能力将冗长的对话历史总结为简洁的摘要，用摘要替换原始消息，释放上下文空间**。

### 触发条件

Compaction 可以在以下情况触发：

1. **自动触发**：当上下文估算用量超过模型限制的一定比例（如 80%），框架自动启动压缩
2. **手动触发**：用户通过 `/compact` 命令主动请求压缩
3. **程序化触发**：通过 API 调用 `session.summarize()` 触发

### 压缩流程

1. **选择压缩点**：框架找到上一次压缩之后的所有消息（即"活跃上下文"）。这些消息将被压缩。

2. **构建压缩 Prompt**：框架向 AI 发送一个特殊的压缩请求，要求它用简洁的语言总结对话历史中的关键信息：
   - 用户的需求和意图
   - AI 已完成的修改和决策
   - 重要的文件路径和代码位置
   - 尚未解决的问题
   - 当前的工作状态

3. **生成摘要**：AI 返回一个结构化的摘要文本。这个摘要远短于原始对话历史。

4. **替换历史**：原始消息被标记为"已压缩"（compacted），在后续的 LLM 调用中不再发送。摘要作为 Compaction Part 插入消息列表，代表被压缩的那段历史。

5. **保留尾部**：压缩点之后的最近几条消息（通常是最后一轮完整对话）不被压缩，保留为"活跃上下文"，确保 AI 不会丢失最近的对话脉络。

### 压缩后的上下文结构

压缩完成后，消息列表的结构变为：

```text
[System Prompt]
[Compaction 摘要 1]  ← 最早的一段对话的摘要
[Compaction 摘要 2]  ← 第二段对话的摘要
...
[Compaction 摘要 N]  ← 最近一次压缩的摘要
[未压缩的活跃消息]   ← 最近几轮对话的完整内容
[当前用户消息]
```

每次新的压缩只压缩"上次压缩之后到当前压缩点之前"的消息，生成新的 Compaction 摘要追加到列表中。这样，AI 始终能看到完整的历史脉络（通过摘要链），同时最近的对话细节保持完整。

### 压缩的智能性

压缩不是简单的截断。AI 在生成摘要时会：
- 保留关键决策和它们的理由
- 保留重要的文件路径和代码片段引用
- 丢弃已完成的中间步骤的细节
- 突出尚未解决的问题

这使得压缩后的摘要比简单的"取最后 N 条消息"更有信息密度。

## 5.4 上下文溢出检测

除了 Token 估算，框架还有多层溢出保护：

### 发送前检查

在发送 LLM 请求前，框架检查估算的 Token 数是否超过模型限制。如果超过，触发自动压缩后再发送。

### API 错误响应

如果 LLM API 返回上下文超限错误（如 Anthropic 的 400 Bad Request "prompt is too long"），框架捕获该错误，强制触发压缩，然后重试请求。

### 最大消息数限制

框架对单次 LLM 调用携带的消息数量有上限。超过上限时，旧消息被自动压缩。

## 5.5 Anthropic Prompt Caching 的集成

Anthropic 的 Claude 模型支持 Prompt Caching——将 System Prompt 和重复使用的上下文标记为"可缓存"，减少重复发送的成本和延迟。

### 缓存断点策略

opencode 在消息转换管道中自动为 Anthropic 模型注入缓存断点（cache breakpoints）：
- System Prompt 和指令文件被标记为可缓存（这些内容在多轮对话中不变）
- 最近几条消息不被缓存（因为它们每轮都在变化）
- 工具定义被标记为可缓存

缓存策略的设计原则是：**缓存那些在多轮对话中保持不变的内容，不缓存每轮都在变化的内容**。

### 缓存效果

通过缓存，重复发送的 System Prompt 和工具定义不再消耗输入 Token 成本，且响应延迟降低。在长对话场景中，缓存带来的节省尤为显著。

## 5.6 长对话场景下的体验保障

综合以上机制，opencode 在长对话场景中的体验保障策略是：

1. **预防**：Token 估算 + 用量可视化，让用户和框架提前感知上下文压力
2. **自动干预**：上下文接近限制时自动压缩，无需用户手动操作
3. **智能压缩**：AI 生成的摘要比机械截断保留更多有用信息
4. **缓存优化**：不变内容被缓存，减少成本和延迟
5. **尾部保留**：压缩后保留最近对话的完整细节，确保 AI 不丢失当前脉络
6. **用户可控**：用户可以随时手动触发压缩、查看上下文用量、或开启新 Session

---

## 本章小结

opencode 的上下文管理是一个多层、主动、智能的系统。它不是被动等待 API 报错，而是主动估算、可视化、自动压缩。Compaction 机制用 AI 自身的能力来总结历史，比简单的截断或滑动窗口保留了更多的信息密度。结合 Anthropic Prompt Caching，在长对话场景中实现了成本、延迟和质量的平衡。
